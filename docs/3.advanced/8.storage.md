# File storage

Storage is what turns `field.file()` and `field.image()` into upload fields, and what puts a media
library in the dashboard. It is off until you configure it, and while it is off none of it exists:
no upload routes, no library page, no sidebar entry.

## Turn it on

Storage is enabled by a single file at the project root. Its default export is a factory that
returns a driver.

::code-group

```ts [eponyme.storage.ts: a bucket]
import { s3 } from '@eponyme/storage/s3'

export default s3({ bucket: 'media', region: 'eu-west-3' })
```

```ts [eponyme.storage.ts: the filesystem]
import { local } from '@karibsen/eponyme/storage'

export default local()
```

::

`@eponyme/storage` ships S3, Cloudflare R2 and Google Cloud Storage drivers, all edge-compatible:

```bash
npm i @eponyme/storage
```

`local()` needs no package and no bucket. It writes to `.eponyme/media` under the working directory
and serves files back through Eponyme's own route, which is enough to develop and to run tests.
It is not meant for production: a second instance cannot see what the first one stored, and nothing
survives a container being replaced.

## Credentials

Credentials never live in `eponyme.storage.ts`. They are read from the environment and handed to
the factory:

```bash [.env]
EPONYME_STORAGE_ACCESS_KEY_ID=…
EPONYME_STORAGE_SECRET_ACCESS_KEY=…
EPONYME_STORAGE_SESSION_TOKEN=…   # optional, for temporary credentials
```

`NUXT_EPONYME_STORAGE_ACCESS_KEY_ID` and friends override them at runtime, the way every Nuxt
runtime config value does. A driver that needs no credentials – `local()` – is given none.

## Options

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  eponyme: {
    storage: {
      prefix: 'uploads',
      maxSize: 25 * 1024 * 1024,
      accept: ['image/*', 'application/pdf'],
    },
  },
})
```

| Option | Default | What it does |
| --- | --- | --- |
| `driver` | `eponyme.storage.ts` | Path to the factory file. Its presence is what enables storage. |
| `prefix` | `uploads` | Key prefix every upload is written under, and **the only part of the bucket the media routes can reach**. |
| `maxSize` | 25 MiB | Largest accepted upload, in bytes. |
| `accept` | `[]` | Media types uploads are restricted to; `image/*` wildcards are understood. Empty accepts anything. |

A field narrows these further with its own `accept` and `maxSize`. It cannot widen them.

## How an upload travels

1. The dashboard asks `POST /api/eponyme-media/upload` for a key, declaring name, type and size.
2. If the driver can presign, the answer is a URL onto the provider and **the bytes never travel
   through your application**. Otherwise the answer points at `PUT /api/eponyme-media/object`,
   which streams them to the driver.
3. The stored value is the URL the file is served from.

Both routes require an `editor` or `owner` session. Uploads are checked twice: once when the key is
reserved, and again on the bytes themselves – a presigned upload is additionally bound to its
declared size by the provider's own signature.

### CORS

A browser may only `PUT` straight to a bucket that allows your origin. Until it does, the preflight
is refused and the upload never leaves the page – so Eponyme retries through its own route instead.
Uploads work either way; without CORS they simply travel through your server.

Allow the origin on the bucket to get the direct path back. On R2:

```json
[
  {
    "AllowedOrigins": ["https://example.com", "http://localhost:3000"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

`AllowedHeaders` must cover every header the signature covers, `content-type` included – the
browser sends them on the preflight and the provider refuses a request missing one.

## What is public

`GET /api/eponyme-media/raw/**` is deliberately unauthenticated. It is the URL saved into an entry
and rendered by your public site, so requiring a session would mean no visitor could load it. Only
the configured `prefix` is reachable through it: it exposes what the dashboard publishes, and
nothing else in the bucket.

With a driver that has a public origin – `publicUrl` on the S3 family – `url()` returns that origin
instead, and this route is never used for reads.

## Deleting

Deleting a file from the library removes it from storage immediately. Entries already pointing at it
keep the URL and will show a missing file, which the confirmation says out loud. Eponyme does not
yet track which entry references which object, so nothing is collected automatically when an entry
is purged or a field is cleared.
