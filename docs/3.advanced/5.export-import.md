# Export and import

Content prepared on a development environment can be moved to production. Both actions live on the
dashboard overview only, because they operate on everything at once.

| Route | Access |
|---|---|
| `GET /api/eponyme-export` | `editor`, `owner` |
| `POST /api/eponyme-import` | `owner` |

## Export

The export carries every singleton and every live collection entry with its complete state (draft,
published, status and publication date), plus a fingerprint of each schema. Collections are read with
one query each.

```json
{
  "eponyme": {
    "format": 1,
    "exportedAt": "2026-07-28T12:00:00.000Z",
    "schemas": { "homepage": "3f2a…", "articles": "9b71…" }
  },
  "entries": [
    { "name": "articles/my-article", "collection": "articles", "draft": {}, "published": {}, "status": "published", "publishedAt": "…" }
  ]
}
```

## Import

An import is a **merge**: each entry overwrites its counterpart, entries absent from the file are
left untouched, and nothing is ever deleted. An entry whose slug is waiting in the trash is skipped
rather than resurrected.

`?dryRun=1` reports what would be created, overwritten and skipped without writing anything, which
is what the dashboard shows before you confirm.

Every imported entry gets one history version with `action: 'import'`, so an import stays reversible
entry by entry.

::important
The whole import is refused, before the first write, when a fingerprint diverges from the local
configuration, and the response names what diverged. The fingerprint covers field names and types
recursively, so relabelling a field or changing a placeholder never blocks an import, while adding
or retyping one does.
::

::note
The import is idempotent, so an interrupted one can simply be replayed. It is not yet wrapped in a
transaction, and the request body is capped at 5 MB, so a very large export would need splitting.
::
