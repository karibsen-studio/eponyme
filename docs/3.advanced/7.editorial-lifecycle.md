# Editorial lifecycle

Eponyme separates the editable draft from the content prepared for public delivery. An entry can be
published immediately, hidden without losing that prepared version, returned fully to draft, or
scheduled with browser-local date and time inputs stored in UTC.

## Actions

| Action | Effect |
|---|---|
| Publish | Copies the current draft to the published content and makes it public immediately |
| Unpublish | Hides the entry while retaining the published content and its publication date |
| Revert to draft | Hides the entry, clears the published content and retains the current draft |
| Schedule | Copies and validates content immediately, then gates visibility with one or two dates |
| Cancel schedule | Clears both scheduled dates without otherwise changing the entry |

Unpublishing and reverting are deliberately different. Republishing an untouched unpublished entry
restores the same prepared content. After reverting, the next publication always uses the current
draft.

On an entry that is already public, the dashboard's **Save** button publishes the current edits.
`Ctrl/Command + S` follows that main button. `Ctrl/Command + D` only saves the draft, so it is the
way to prepare changes while the previous published version stays online.

## Visibility does not depend on a scheduler

Every public read applies the same rule:

```text
status is published
and scheduledPublishAt is empty or has passed
and scheduledUnpublishAt is empty or is still in the future
```

A publication becomes visible exactly at its scheduled time. An unpublication stops being visible
exactly at its scheduled time. This is evaluated by singleton reads, collection listings and the
sitemap, so no background process is required for database correctness.

## Materialize scheduled transitions

Call the auto-imported `runEponymeSchedule()` from infrastructure you protect yourself: a Nitro
task, a private route, or an external cron. Eponyme deliberately does not expose a write endpoint or
invent an authentication token.

```ts [server/api/internal/eponyme-schedule.post.ts]
export default defineEventHandler(async (event) => {
  await requireYourInternalAuthentication(event)
  return await runEponymeSchedule()
})
```

Materialization clears due dates, writes history, emits `eponyme:entry:published` or
`eponyme:entry:unpublished`, and is idempotent. Those hooks are what let an application purge its
CDN at the scheduled instant. Without a call, database reads still transition on time, while a CDN
may keep its previous response until `s-maxage` expires. The default in-memory row cache catches up
within five seconds.

## Turn the publication tab off

`publication: false` removes the publication tab from every editor.

```ts [nuxt.config.ts]
eponyme: { publication: false }
```

A record answers per entry instead, keyed by singleton name or by collection name the way
`previewPaths` is. A name it does not carry keeps its tab, so this is how a single page loses its
lifecycle while the rest of the dashboard keeps one.

```ts [nuxt.config.ts]
eponyme: {
  publication: {
    'pages/homepage': false,
    articles: false,
  },
}
```

A collection overrides both with its own option, in either direction — it is the only way to
enable the tab for one collection while `publication: false` disables it everywhere else.

```ts [eponyme.config.ts]
releases: collection({
  publication: false,
  titleField: 'title',
  slugField: 'slug',
  fields: { title: field.string({ required: true }), slug: field.slug({ required: true }) },
})
```

Publishing and saving a draft stay in the editor toolbar, so what disappears is scheduling,
unpublishing, reverting to draft and the status panel. `PATCH /api/eponyme/<name>` answers 422 to
those three actions, so an editor holding a tab opened before the change cannot still send them.
`unschedule` stays allowed: an entry scheduled beforehand must be able to lose its dates.

## Existing installations must migrate first

Add the nullable `scheduledPublishAt` and `scheduledUnpublishAt` columns and their indexes before
deploying this version. Eponyme does not currently run or verify consumer-owned Prisma migrations at
startup. Missing columns therefore do not prevent the server from booting, but the first content
read fails. The complete schema is available in the installation guide.
