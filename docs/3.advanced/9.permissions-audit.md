# Roles, permissions and audit

Eponyme keeps `viewer`, `editor` and `owner` as built-in profiles. An application can add roles in
`eponyme/roles.ts`; the developer defines what those roles may do, then an owner assigns one role to
each account from the dashboard.

## Declare application roles

```ts [eponyme/roles.ts]
import { defineEponymeRoles, permission } from '@karibsen/eponyme/config'

export default defineEponymeRoles({
  contributor: {
    label: 'Contributor',
    description: 'Can prepare article drafts without publishing them.',
    permissions: [
      permission.allow(
        ['content.read', 'content.create', 'content.update'],
        permission.collection('articles'),
      ),
    ],
  },
  publisher: {
    label: 'Publisher',
    description: 'Can publish stored drafts without changing their content.',
    permissions: [
      permission.allow(
        ['content.read', 'content.publish', 'content.unpublish', 'content.schedule'],
        permission.collection('articles'),
      ),
    ],
  },
})
```

The file belongs to the application, next to `eponyme.config.ts`. The dashboard does not edit role
definitions: keeping them in source control makes permission changes reviewable and deployable with
the application. The Users page lists both built-in and application roles.

A role can target a singleton, collection, form, folder or system feature:

```ts [eponyme/roles.ts]
permissions: [
  permission.allow('content.read', permission.folder('marketing')),
  permission.allow('submissions.read', permission.form('contact')),
  permission.allow(['media.read', 'media.upload'], permission.system('media')),
  permission.deny('content.update', permission.singleton('marketing/legal')),
]
```

Folder rules apply to descendants. Neither a folder rule nor `permission.all()` ever reaches a
system feature: `permission.system('media')` is the only way to open the media library, whatever a
content folder is named. An exact deny always wins over an inherited or global allow.
Unknown resources and roles fail during startup, and a session whose role was removed from the file
is rejected instead of falling back to another role.

Available content actions are `read`, `create`, `update`, `publish`, `unpublish`, `schedule`, `trash`,
`restore`, `purge`, `export` and `import`. Forms separate submission reads and deletes; media separates
reads, uploads and deletes. `content.purge`, `content.import`, `users.manage` and `audit.read` remain owner-only and
cannot be granted to an application role.

The dashboard hides resources and actions the current role cannot use, but the API performs the same
check independently on every private route. Publishing consumes the draft already stored by a prior
save, so a publisher cannot smuggle content changes through the publication action.

## Audit log

Owners can open **Audit log** from the dashboard. It records successful and failed sign-ins with the
date, account name, IP address and user agent, plus sign-outs, password changes and resets, account
and role changes, editorial transitions, trash, restore and purge operations, imports, media changes,
and submission deletions.

Event metadata is bounded and removes keys that can carry passwords, secrets, tokens, cookies or
content payloads. Content writes and their audit events share the same database transaction.

Audit events are retained for 365 days by default. One instance claims the cleanup job, then removes
expired rows in bounded batches; other instances skip that interval.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  eponyme: {
    audit: {
      retentionDays: 365,
      pruneIntervalHours: 24,
    },
  },
})
```
