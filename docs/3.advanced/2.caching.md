# Caching

Published content is identical for every visitor, so it can be cached aggressively. Everything
unreleased answers `Cache-Control: no-store` and is never stored anywhere.

## What Eponyme does on its own

A public read answers with three windows, configured in `nuxt.config`:

```
Cache-Control: public, max-age=30, s-maxage=300, stale-while-revalidate=3600
```

- `max-age` is the browser's, and **a browser cache cannot be purged** by anyone. Whatever it holds
  is served until it expires, publication or not, which is why `browserCacheSeconds` stays short.
- `s-maxage` is the CDN's, and a CDN can be purged, so `cdnCacheSeconds` can afford to be generous.
- `cacheSeconds` is an in-memory window per server instance, so a page reading the same entry from a
  singleton, a listing and a layout pays one round trip instead of three.

## Cache tags

A CDN is usually purged by tag rather than by URL, and one entry appears in more than one cached
response. Eponyme tags all of them:

| Response | `Cache-Tag` |
|---|---|
| `/api/eponyme/articles/my-article` | `eponyme,eponyme:articles/my-article,eponyme:articles` |
| the page `/articles/**` | `eponyme,eponyme:articles` |
| the page `/` for a singleton | `eponyme,eponyme:homepage` |

Both `Cache-Tag` and `Vercel-Cache-Tag` are sent, so the same deployment can move between CDNs
without a code change. The page routes are tagged from `previewPaths` at build time, and the module
logs which routes it tagged, because writing into your `routeRules` would otherwise be invisible to
whoever reads that file.

A collection route cannot name a slug in a route rule, so its pages carry the collection tag:
publishing one article purges every article page and the index that lists them. Broader than
strictly needed, and never wrong. Headers you set yourself are never overwritten.

## Purging on publication

```ts [server/plugins/eponyme-purge.ts]
import { invalidateByTag } from '@vercel/functions'

export default defineNitroPlugin((nitroApp) => {
  const purge = async ({ name, collection }: { name: string, collection?: { name: string } }) => {
    if (!process.env.VERCEL) return
    try {
      await invalidateByTag(getEponymeCacheTags(name, collection))
    }
    catch (error) {
      // A publication that reached the database succeeded. Content still appears once the
      // CDN window runs out on its own.
      console.error('[eponyme] CDN purge failed, falling back to expiry', error)
    }
  }

  nitroApp.hooks.hook('eponyme:entry:published', purge)
  nitroApp.hooks.hook('eponyme:entry:restored', purge)
  nitroApp.hooks.hook('eponyme:entry:trashed', purge)
  nitroApp.hooks.hook('eponyme:entry:untrashed', purge)
  nitroApp.hooks.hook('eponyme:entry:purged', purge)
})
```

::note
`getEponymeCacheTags()` always includes the global `eponyme` tag alongside the precise ones, so
passing the whole array purges everything Eponyme tagged. Drop `'eponyme'` from the call if you want
surgical purges.
::

## Making a whole page cacheable

By default a page is server-rendered on every visit: the cold load costs no API round trip (the
render reads the database in-process), but the **first client-side navigation to each page** costs
one small request per entry, with a brief loading state.

To remove that, cache the page itself. Nothing is prebuilt: the route is still rendered on demand,
then served from the cache.

```ts [nuxt.config.ts]
routeRules: {
  '/': { swr: 600, isr: 600, payload: true },
  '/articles/**': { swr: 600, isr: 600, payload: true },
}
```

- `payload: true` is what makes a `NuxtLink` navigation free: the entry travels with the page
  instead of being fetched again. It only works on a cached or prerendered route.
- `isr` is written into a per-route config by the Vercel preset and does nothing elsewhere; `swr` is
  nitro's own cache. Declaring both means `node .output/server/index.mjs` behaves like production, so
  the setup can be verified before a deploy.

With a purge wired to publication, the expiry is only a safety net for when that purge fails.

::warning
`payload: true` alone does nothing: nitro only serves a `_payload.json` for a route that is
prerendered or cached.
::
