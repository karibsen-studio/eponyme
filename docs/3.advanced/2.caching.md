# Caching

Published content is identical for every visitor, so it can be cached aggressively. Everything
unreleased answers `Cache-Control: no-store` and is never stored anywhere.

## What Eponyme does on its own

A public read answers with three windows, configured in `nuxt.config`:

```
Cache-Control: public, max-age=30, s-maxage=300, stale-while-revalidate=3600
```

- `max-age` is the browser's, and **a browser cache cannot be purged** by anyone. Whatever it holds
  is served until it expires, publication or not, which is why `browserCacheSeconds` stays short.
- `s-maxage` is the CDN's, and a CDN can be purged, so `cdnCacheSeconds` can afford to be generous.
- `cacheSeconds` is how long content already read may be reused, so a page reading the same entry
  from a singleton, a listing and a layout pays one round trip instead of three.

## Sharing the content cache through Redis

By default that last window lives in the memory of each server instance, which makes a save clear
only the instance that served it. On a single instance that is invisible; on several, one of them
can keep answering with the previous content until its window expires.

Point `cacheStorage` at a [Nitro storage mount](https://nitro.build/guide/storage) and the cache
becomes shared, so an invalidation reaches every instance at once:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    storage: {
      eponyme: { driver: 'redis', url: process.env.REDIS_URL, base: 'eponyme' },
    },
  },
  eponyme: {
    cacheStorage: 'eponyme',
    cacheSeconds: 60,
  },
})
```

Keys are namespaced by the driver's `base`, so a Redis shared with something else stays readable:

```
eponyme:row:homepage
eponyme:row:articles:hello-world
eponyme:rows:articles:published
eponyme:rows:articles:sitemap
```

`base` is the only thing separating one deployment from another, so give it the environment and the
site rather than the module name alone. Two deployments sharing a Redis and a `base` read each
other's content, and a release that changes how an entry is stored keeps answering with what the
previous one wrote until every window expires:

```ts
base: 'prod:karibsen:eponyme'
```

Adding the release to it, `prod:karibsen:eponyme:v12`, makes a deployment start on an empty cache
instead. That costs one round of database reads and removes any question about what a rollback
serves.

`unstorage` ships the Redis driver, but the client is yours to install – `npm i ioredis` – so a
deployment that caches in memory does not carry one it never builds.

A small in-process tier stays in front of the shared one. It coalesces the concurrent reads of a
single render and answers repeats without a network hop, at the cost of an instance possibly
missing an invalidation for up to a second. Without a shared tier there is nothing behind it, so it
holds a value for the full `cacheSeconds` instead, and a save then clears only the instance that
served it. Redis being unreachable is treated as a cache miss, never an error: reads fall through
to the database, and the failure is logged and sent to the `eponyme:cache:failed` hook rather than
raised.

## Invalidating a read that started before the save

A read that started before a save answers after it, holding content the save has already replaced.
Writing that to the shared tier would put the previous version back for a whole window, which is
the one thing an invalidation is there to prevent. So an invalidation also replaces a token stored
beside the content, and a read whose token moved while it was in flight returns its value without
caching it. That is what makes an invalidation hold across instances: an in-process guard only
covers the one that served the save.

::note
With `cacheStorage` set, `cacheSeconds` can be raised well beyond its default – the reason to keep
it short was that nothing could purge it.
::

### Rate limiting follows

Login and managed-form rate limits are counted in PostgreSQL by default, which already makes them
shared across instances. When `cacheStorage` resolves to Redis, they move there automatically –
same mount, no second option to configure – and are counted with `INCR` against an expiring key,
which is markedly cheaper than an upsert plus a periodic sweep:

```
eponyme:ratelimit:<scope hash>:<window>
```

The move only happens when the mount exposes a client that can increment atomically. Any other
driver keeps counting in PostgreSQL, because a limiter built on a read-then-write loses hits under
exactly the concurrency it exists to survive. If Redis becomes unreachable, hits are counted in the
database rather than allowed through.

## Cache tags

A CDN is usually purged by tag rather than by URL, and one entry appears in more than one cached
response. Eponyme tags all of them:

| Response | `Cache-Tag` |
|---|---|
| `/api/eponyme/articles/my-article` | `eponyme:articles/my-article,eponyme:articles` |
| the page `/articles/**` | `eponyme:articles` |
| the page `/` for a singleton | `eponyme:homepage` |
| `/api/eponyme-sitemap` | `eponyme,eponyme:sitemap` |

The bare `eponyme` tag is the exception, and it is deliberate. `getEponymeCacheTags` includes it in
what a purge names, so it is reserved for the few responses that every publication invalidates: a
sitemap lists whatever is online, so it is tagged with it. Put it on an ordinary page and you get
the opposite of tagging, since publishing anything would then purge the whole site. Use
`getEponymeResponseTags` when you tag a route of your own.

Both `Cache-Tag` and `Vercel-Cache-Tag` are sent, so the same deployment can move between CDNs
without a code change. The page routes are tagged from `previewPaths` at build time, and the module
logs which routes it tagged, because writing into your `routeRules` would otherwise be invisible to
whoever reads that file.

A collection route cannot name a slug in a route rule, so its pages carry the collection tag:
publishing one article purges every article page and the index that lists them. Broader than
strictly needed, and never wrong. Headers you set yourself are never overwritten.

One preview path cannot be tagged: a collection served from the root, `'/:slug'`. There is no prefix
to turn into a glob, and `/**` would put the tag on every route of the site, the dashboard and the
API included, so a single publication would purge all of it. Eponyme leaves that collection untagged
and says so at build time. Tag the routes that show it yourself:

```ts
routeRules: {
  '/baby-athle': { headers: { 'Cache-Tag': 'eponyme:pages', 'Vercel-Cache-Tag': 'eponyme:pages' } },
}
```

## Purging on publication

```ts [server/plugins/eponyme-purge.ts]
import { invalidateByTag } from '@vercel/functions'
import type { EponymeEntryContext, EponymeEntryTrashContext } from '@karibsen/eponyme'

export default defineNitroPlugin((nitroApp) => {
  const purge = async ({ name, collection }: EponymeEntryContext | EponymeEntryTrashContext) => {
    if (!process.env.VERCEL) return
    try {
      await invalidateByTag(getEponymeCacheTags(name, collection))
    }
    catch (error) {
      // A publication that reached the database succeeded. Content still appears once the
      // CDN window runs out on its own.
      console.error('[eponyme] CDN purge failed, falling back to expiry', error)
    }
  }

  nitroApp.hooks.hook('eponyme:entry:published', purge)
  nitroApp.hooks.hook('eponyme:entry:unpublished', purge)
  nitroApp.hooks.hook('eponyme:entry:scheduled', purge)
  nitroApp.hooks.hook('eponyme:entry:unscheduled', purge)
  nitroApp.hooks.hook('eponyme:entry:restored', purge)
  nitroApp.hooks.hook('eponyme:entry:trashed', purge)
  nitroApp.hooks.hook('eponyme:entry:untrashed', purge)
  nitroApp.hooks.hook('eponyme:entry:purged', purge)
})
```

::note
`getEponymeCacheTags()` always includes the global `eponyme` tag alongside the precise ones, so
passing the whole array also drops whatever you tagged globally, a sitemap being the usual case.
Drop `'eponyme'` from the call if you want to leave those alone.
::

::warning
On Vercel this plugin is not enough on its own. A response header does not tag an ISR entry, so the
purge finds nothing and reports success. See **Tagging ISR responses on Vercel** below.
::

An import emits one hook per entry it wrote, chosen from the same set: `published` for an entry it
publishes, `unpublished` for one that was published and no longer is, and `saved` for a write that
never reached the public site. So the plugin above already covers an import, and only content the
import took down or put up is purged.

## Making a whole page cacheable

By default a page is server-rendered on every visit: the cold load costs no API round trip (the
render reads the database in-process), but the **first client-side navigation to each page** costs
one small request per entry, with a brief loading state.

To remove that, cache the page itself. Nothing is prebuilt: the route is still rendered on demand,
then served from the cache.

```ts [nuxt.config.ts]
routeRules: {
  '/': { swr: 600, isr: 600 },
  '/articles/**': { swr: 600, isr: 600 },
},
experimental: {
  // See "Payload extraction" below. Leave this at its default and a cached page and its
  // payload become two cache entries that drift apart.
  payloadExtraction: 'client',
},
```

- `isr` is written into a per-route config by the Vercel preset and does nothing elsewhere. `swr` is
  nitro's own cache, and the Vercel preset ignores it when `isr` is set on the same rule. Declaring
  both means `node .output/server/index.mjs` behaves like production, so the setup can be verified
  before a deploy.
- A `NuxtLink` navigation stays cheap because Nuxt extracts the page payload on its own. There is no
  `payload` route rule to enable it: see below.

With a purge wired to publication, the expiry is only a safety net for when that purge fails.

A scheduled transition only emits its publication or unpublication hook when
`runEponymeSchedule()` materializes it. Without that call, database reads still switch at the exact
time, but an already cached CDN response remains available until `s-maxage` expires. The in-process
row cache has a five-second default TTL and corrects itself without a write.

### Payload extraction

Caching a page turns payload extraction on for the whole application: Nuxt enables it as soon as one
route rule carries `isr` or `cache`. At its default value, `true`, the payload is extracted to a
separate `_payload.json` **for the initial server render as well as for client-side navigation**.

That is one page and two independent cache entries, each with its own age. They drift apart, and the
browser then renders a correct document and corrects it with stale data during hydration. Two entries
appear merged, a title carries another entry's image, an entry you just published vanishes on load.

```ts [nuxt.config.ts]
experimental: {
  payloadExtraction: 'client',
}
```

`'client'` inlines the payload in the server-rendered HTML and extracts it only for client-side
navigation. The initial document becomes consistent with itself, and navigation stays as fast.

::warning
There is no `payload` route rule. `{ payload: true }` in `routeRules` is not part of
`NitroRouteConfig` and is silently ignored. Payload extraction is controlled by
`experimental.payloadExtraction` alone.
::

## Tagging ISR responses on Vercel

Vercel keeps two different stores. The CDN cache holds a response tagged by the `Vercel-Cache-Tag`
header it carried. ISR entries, the ones a `isr` route rule produces, are held by the prerender layer
and **are not tagged by that header**.

The consequence is quiet. `invalidateByTag` resolves without doing anything when it finds no entry,
and `@vercel/functions` also resolves without an error when the platform exposes no purge API at all:

```ts
const invalidateByTag = (tag) => {
  const api = getContext().purge
  if (api) return api.invalidateByTag(tag)
  return Promise.resolve()
}
```

So a purge can be sent with the right tags, log nothing, and leave every page untouched until its
expiry. Add `addCacheTag` at render time, which tags the entry itself:

```ts [server/plugins/eponyme-cache-tag.ts]
import { addCacheTag } from '@vercel/functions'
import { getRouteRules } from 'nitropack/runtime'

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('render:response', async (_response, { event }) => {
    if (!process.env.VERCEL) return
    const tags = getRouteRules(event).headers?.['Cache-Tag']
    if (!tags) return
    try {
      await addCacheTag(tags.split(',').filter(Boolean))
    }
    catch (error) {
      // A rendered page is still a rendered page. Untagged, it waits for its expiry.
      console.error('[eponyme] addCacheTag failed', error)
    }
  })
})
```

It reuses the tags the route rule already declared, so nothing is configured twice. Keep the headers
as well: they are what a non-Vercel CDN reads.

### Proving that a purge works

A `Cache-Tag` in the response proves nothing about the stored entry. The test that does:

1. Pick a page with a long window and load it, so it is cached and fresh.
2. Wait, then publish anything that carries one of its tags.
3. Request it once and read `x-vercel-cache`.

`STALE` well before the window elapsed means the purge reached it. `HIT` on the same
`last-modified` until the window runs out means it did not.

::note
`invalidateByTag` marks entries stale rather than deleting them, so the first visitor after a
publication still receives the previous copy while the new one renders in the background. Use
`dangerouslyDeleteByTag` if the very first request has to be correct, keeping in mind that a
collection tag covers many pages at once.
::

## When a publication does not show up

Work down the chain. Each step rules out one cause.

1. **The API**, which is the source of truth. `GET /api/eponyme-collections/<name>` and read `status`
   and `publishedAt`. If the entry is wrong here, nothing downstream matters.
2. **The served HTML and its headers.** Read `age`, `x-vercel-cache` and `last-modified`. Compare
   `last-modified` with the time of the publication: a copy generated before it explains everything,
   and the only question left is why it was not purged.
3. **The payload**, when the page has one. If the HTML and the `_payload.json` disagree, see
   **Payload extraction**.
4. **The purge**, in your platform's runtime logs. Log the tags you send, otherwise a purge that
   never leaves looks exactly like one that worked.
5. **The tagging**, with the test above.

Two traps worth knowing.

A page keeps the state of the world at the moment it was regenerated. Unpublishing an entry and then
loading the page to check makes that page regenerate inside the window where the entry is gone, and
it keeps that state until it expires or is purged. The page that looks broken is rarely the one at
fault, it is simply the one that was rendered at the wrong second.

Polling a deployed site in a loop to watch a cache is a good way to be served a bot challenge, which
answers `403` to anything that cannot run its JavaScript. Space the measurements out, or read the
platform logs instead.
