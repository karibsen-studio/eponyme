# Configuration

Everything lives under the `eponyme` key of `nuxt.config`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@karibsen/eponyme'],
  eponyme: {
    prismaClient: '~~/server/utils/prisma',
    dashboardPath: '/__eponyme',
    previewPaths: {
      homepage: '/',
      articles: '/articles/:slug',
    },
    colorPresets: [
      { label: 'Ink', value: '#171714' },
      '#ffffff',
    ],
    publication: {
      'pages/homepage': false,
    },
    auth: {
      sessionDurationDays: 7,
    },
    audit: {
      retentionDays: 365,
      pruneIntervalHours: 24,
    },
    rateLimits: {
      loginPerIp: 10,
      loginGlobal: 300,
      loginAccountFailures: 5,
      formPerIp: 5,
      formGlobal: 100,
    },
    cacheSeconds: 5,
    autoReindex: true,
    browserCacheSeconds: 30,
    cdnCacheSeconds: 300,
  },
})
```

## Options

| Option | Default | What it does |
|---|---|---|
| `prismaClient` | *required* | Module specifier of a server file whose default export is an initialised `PrismaClient`. The build fails without it |
| `dashboardPath` | `/__eponyme` | Route the dashboard is served on. Surrounding slashes are normalised, so `__eponyme` and `/__eponyme/` are equivalent |
| `previewPaths` | `{}` | Public route rendering each entry. A collection value must contain `:slug` |
| `colorPresets` | `[]` | Palette offered by every color field, unless the field sets its own `presets` |
| `publication` | `true` | Whether the editor offers the publication tab. A boolean answers for every entry, a record answers per singleton or collection name. A collection overrides both. See [Editorial lifecycle](/advanced/editorial-lifecycle) |
| `auth.sessionDurationDays` | `7` | Session lifetime in days, counted from sign-in and never extended by activity |
| `audit.retentionDays` | `365` | Number of days audit events are kept |
| `audit.pruneIntervalHours` | `24` | Minimum interval between distributed audit cleanup jobs |
| `rateLimits.loginPerIp` | `10` | Login attempts per client address and minute |
| `rateLimits.loginGlobal` | `300` | Login attempts across the deployment and minute |
| `rateLimits.loginAccountFailures` | `5` | Failed login attempts per account and 15 minutes; successful credentials are never blocked by this counter |
| `rateLimits.formPerIp` | `5` | Managed-form submissions per client address, form and minute |
| `rateLimits.formGlobal` | `100` | Managed-form submissions per form across the deployment and minute |
| `cacheSeconds` | `5` | How long a server instance may reuse content it has already read. `0` disables it |
| `autoReindex` | `true` | Rebuild the filterable index at startup when the configuration that produced it has changed. See below |
| `browserCacheSeconds` | `30` | How long a browser may reuse published content. `0` disables it |
| `cdnCacheSeconds` | `300` | How long a CDN may reuse published content. `0` disables it |
| `locale` | English | Language of the dashboard interface, resolved once at build time. See [Dashboard language](/advanced/locale) |

Rate-limit counters are shared by every Nitro instance. A Redis `cacheStorage` mount is reused when
it exposes an atomic counter; otherwise PostgreSQL remains the safe default and fallback. Keep an
edge/CDN rate limit as the first layer, especially when the origin is public.

## previewPaths

This map is read three times over: to build preview URLs for the dashboard, to list the sitemap,
and to attach cache tags to those routes so a publication can purge them.

```ts
previewPaths: {
  // a singleton, by its exact name
  'homepage': '/',
  'pages/legal': '/legal',
  // a collection, by its name, with `:slug` replaced per entry
  'articles': '/articles/:slug',
}
```

An entry left out of the map is still editable: it simply has no public URL Eponyme can name, so
it gets no preview, no sitemap entry and no cache tag.

## The three cache windows

They are deliberately different, because they cannot be invalidated in the same way.

| Window | Sent as | Can it be purged? |
|---|---|---|
| `cacheSeconds` | nothing, it is in-memory per server instance | a save clears it on the instance that served it |
| `browserCacheSeconds` | `max-age` | **no**, never, so keep it short |
| `cdnCacheSeconds` | `s-maxage`, plus `stale-while-revalidate` twelve times longer | yes, by tag |

## autoReindex

Filtering a collection with `where` reads a denormalised index rather than the entries
themselves. Saving an entry rewrites its index rows in the same transaction, so the index
stays current on its own – with one exception.

Making a field filterable, by adding a `field.tags()` or a `field.select()` to a collection
that already holds entries, leaves those entries without a row for the new key. A filter on
it would then answer "no matching entries" rather than failing, and entries created *after*
the change would still be found – a collection that looks like it works.

So at startup Eponyme compares a fingerprint of each collection's filterable fields against
what it last indexed, and rebuilds only what changed. An unchanged configuration costs one
read of a table holding one row per collection. Nothing to run by hand.

The fingerprint covers everything that can change a stored value – options, defaults, the
choices of a `select` – and ignores what cannot, such as a label. It cannot see inside a
custom `validate`: changing one so that it rejects values already stored needs a manual
[`reindexEponymeEntries()`](/content/composables).

Set `autoReindex: false` only as an escape hatch, if a rebuild ever fails on every boot and
you need the application up while you investigate.

## Roles

The built-in profiles remain available:

- `owner` manages content and users.
- `editor` manages content.
- `viewer` has read-only dashboard access.

An application can declare additional roles and granular permissions in `eponyme/roles.ts`.
Definitions stay in developer-owned source code; owners assign those roles to accounts in the
dashboard. Permissions are enforced on the server, never in the interface alone.
